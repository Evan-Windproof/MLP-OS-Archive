# MLP OS Archive — Project Inclusion Policy

**Policy version:** 1.0  
**Status:** Active  
**Applies to:** New submissions, historical records, and updates to existing records

This policy is the authoritative standard for deciding which projects belong in MLP OS Archive. The submission guide explains how to submit; the historical archive guide explains how to document evidence, releases, screenshots, and files.

## 1. Purpose and scope

MLP OS Archive is an independent, non-commercial fan archive documenting computer projects with substantive My Little Pony (MLP) content.

The archive accepts three categories:

### 1.1 Independent operating systems

Examples include:
- Operating systems with independently developed or substantially adapted kernels.
- Independent systems built on another kernel but developed as distinct operating-system projects.
- Experimental, prototype, unfinished, discontinued, and historically significant operating systems.

### 1.2 Linux distributions

Examples include:
- MLP-themed Linux distributions.
- Substantially customized distributions based on an existing Linux distribution.
- Projects with a distinct system configuration, desktop environment, package selection, system components, or coherent MLP integration.

A standard Linux distribution with only an MLP wallpaper, a renamed ISO, or a few cosmetic changes is not a distinct MLP distribution.

### 1.3 Desktop themes and operating-system customizations

Examples include:
- Windows, Linux, and other desktop themes.
- Window decorations, icon sets, cursors, login or boot screens, and system sounds.
- Rainmeter skins and comparable desktop widgets.
- Coherent theme packs, desktop customization collections, and other OS-integrated visual or interaction customizations.

A qualifying desktop customization does not need to be a complete operating system. Individual theme works may be grouped into a creator or series collection when that makes the archive clearer, while retaining each work's identity and source.

Standalone wallpapers, illustrations, fan art, or unrelated applications are outside the scope unless they form part of a qualifying OS or desktop customization project.

## 2. MLP relevance

The project's actual content must contain recognizable MLP-related elements. A name, version number, developer nickname, community affiliation, or marketing description alone is not sufficient.

MLP content may include characters, locations, symbols, visual design, sounds, terminology, or other clearly identifiable elements from My Little Pony.

### 2.1 Graphical operating systems

A graphical OS project should demonstrate at least three of the following:

- MLP-themed desktop wallpaper or desktop background.
- MLP-themed shell commands, terminal interface, or system interaction.
- MLP-themed windows, controls, or desktop environment.
- MLP-themed system icons or cursors.
- MLP-themed boot screen or login screen.
- MLP-themed system sounds.
- MLP-themed system applications or desktop widgets.

The elements must be part of the actual project, not merely shown in an unrelated promotional mockup.

### 2.2 Text-based operating systems

A text-based OS does not need a graphical desktop. It must include meaningful MLP integration in its actual user-facing system experience, such as MLP-themed shell commands, terminal presentation, startup messages, prompts, or ASCII artwork. A single unrelated easter egg is not sufficient.

### 2.3 Linux distributions

A Linux distribution must provide substantive MLP integration across the system or its desktop experience. A wallpaper-only respin or a few isolated cosmetic changes do not qualify as a distinct MLP distribution. A coherent desktop theme that independently meets section 1.3 may instead be considered under Desktop themes and operating-system customizations.

### 2.4 Desktop customization projects

A desktop customization must have a clear operating-system or desktop-environment use and demonstrable MLP content. A coherent theme pack, icon set, cursor theme, or desktop widget collection may qualify individually; a single standalone wallpaper does not.

### 2.5 Project names

The project name does not need to contain MLP, Pony, Equestria, or a character name. A project with an unrelated name may qualify if its actual content meets this policy.

## 3. Development and completion requirements

### 3.1 Submitter's own projects

A person submitting their own operating-system project must have started actual development. Evidence may include source code, a working or partially working prototype, a reproducible build, a boot attempt, or a technical development log.

A proposal consisting only of an idea, plan, concept art, or future roadmap is not eligible as a completed archive record. It may be retained as a research lead only when it has a meaningful public source and is relevant to the archive.

Projects do not need to be ready for daily use. Experimental, pre-alpha, alpha, beta, and incomplete projects may qualify when actual work exists.

### 3.2 Third-party and historical projects

Historical projects do not need to remain active, downloadable, or executable. A project may qualify when it is discontinued, abandoned, unfinished, lost, or represented only by source code, original pages, screenshots, release announcements, or other traceable historical evidence.

The stricter requirement for a submitter's own planned project does not exclude a third-party historical project merely because its development stopped early.

## 4. Evidence and historical records

### 4.1 Preferred evidence

Prefer sources in this order, while considering the context and reliability of each source:

1. Original project website, repository, release page, or creator's own publication.
2. Original development logs, announcements, forum posts, and contemporaneous documentation.
3. Stable historical captures from services such as the Internet Archive.
4. Independent contemporary coverage or community records that identify the project and its creator.
5. Later retrospective accounts that can be traced to identifiable sources.

Search snippets, AI-generated summaries, unattributed reposts, and unsupported recollections are leads, not sufficient evidence on their own.

### 4.2 What to document

Record as much as sources support:
- Original project name, aliases, and distinct same-name projects.
- Developer or team, with attribution source.
- Project type, base system, kernel, desktop environment, and platform.
- Creation dates, release dates, versions, and development milestones.
- Original website, source repository, documentation, and download links.
- Screenshots, their original source, creator credit, and known usage terms.
- License and copyright notices.
- Current development and download availability, including when these were checked.

Do not guess missing facts. Use Unknown, Unverified, or an explicit note where appropriate. Distinguish a project's original release date from a mirror date, archive capture date, or retrospective article date.

### 4.3 Lost or unavailable projects

A project may be included even when its original download is gone, provided reliable evidence establishes its identity and relevant MLP content. Clearly distinguish:
- Original download available from the publisher.
- Third-party mirror available.
- Historical download link now unavailable.
- Download availability not yet checked or not confirmed.

Do not label a file as available unless the linked asset is actually accessible and its provenance is understood. Do not imply that a project was successfully executed merely because a download or source archive exists.

## 5. Duplicate projects, versions, forks, and collections

### 5.1 Duplicate checks

Before creating a record, compare the project's canonical name, aliases, developer, dates, source URLs, base system, kernel, and project history against existing records.

A shared name does not prove that two projects are the same. Projects with different developers, codebases, kernels, base systems, or historical records may require separate entries. Use explicit edition or platform labels to disambiguate same-name projects.

### 5.2 Versions

Keep versions of the same continuing project in one record and document them in its release history when appropriate. Create separate records only when a version represents a genuinely distinct project identity.

### 5.3 Forks and derivatives

A fork may be independently catalogued when it has a distinct identity and substantive development or customization. A name change, wallpaper swap, or trivial configuration change alone does not establish a separate project.

### 5.4 Creator series and collections

Related works by one creator may be grouped into a collection record. Preserve the individual work names, original URLs, versions, dates, credits, and license information wherever known. Do not describe a collection of desktop themes as a standalone operating system or imply that separate works form one installer.

## 6. Exclusions

Do not formally include:
- Projects with no substantive MLP connection.
- Ordinary software, games, websites, or fan art unrelated to operating systems or desktop customization.
- Projects whose only MLP connection is their name, version number, author nickname, or community affiliation.
- A submitter's own OS proposal when no actual development has begun.
- A standard Linux distribution with only a wallpaper or a few superficial changes, unless a separate qualifying desktop customization is being catalogued.
- Duplicate records without a distinct project identity.
- Claims or assets that cannot be responsibly documented or whose publication would create a clear rights or safety problem.
- Malware, malicious bundles, or projects whose distribution would create an evident risk to users.

Insufficient evidence should normally result in a research lead or a request for clarification, not an unsupported conclusion that a historical project never existed.

## 7. Copyright, attribution, and intellectual property

### 7.1 MLP rights and independence

My Little Pony characters, names, artwork, and other protected elements belong to their respective rights holders. MLP OS Archive is an unofficial, independent, non-commercial fan archive. It is not authorized, endorsed, or sponsored by Hasbro or its subsidiaries.

The archive does not claim ownership of MLP intellectual property or of third-party project materials.

### 7.2 Link-first preservation

The default approach is to document projects and link to their original sources. A record of a file's existence does not require the archive to host or redistribute that file.

Do not copy or mirror ISO images, installers, theme packs, artwork, screenshots, source archives, or other third-party assets unless redistribution is clearly permitted by the applicable license or explicit permission.

Do not remove creator credits, copyright notices, or license terms. Do not present another creator's work as archive-original material.

### 7.3 Screenshots and other media

Prefer linking to the original image or source page. Before rehosting an image, verify its license or obtain permission. Record the creator, source, and known terms. If reuse rights are unclear, link to the source rather than copying the asset. Do not hotlink or embed an image when the source's terms or technical restrictions prohibit it.

### 7.4 Copyright concerns

The archive does not make legal determinations. If a credible rights concern is raised, review the affected record and pause display or distribution of the disputed asset when appropriate. Correct attribution, replace the asset with a source link, or remove it when warranted. Avoid publishing private information in the process.

## 8. Review workflow and status labels

### 8.1 Internal research states

These labels describe the archive's research workflow and are not project development states:

- **Lead:** A possible project has been found, but its identity or relevance is not established.
- **Identified:** The project identity is established; material details may still need checking.
- **Pending Review:** Evidence has been gathered and the record is awaiting maintainer review.
- **Accepted:** The record has passed review and may be published after merge and deployment.
- **Duplicate:** The submission refers to an existing project record.
- **Excluded:** The project does not meet the scope or cannot responsibly be published.

### 8.2 Public record verification states

Use the repository's supported verification values:

- **Unverified:** Material claims have not yet been established.
- **Partially Verified:** Sources support some material claims, while other important details remain uncertain.
- **Verified:** Reliable evidence supports the project identity and the material claims actually published. First-party evidence may be sufficient; every optional field need not be known.
- **Unable to Verify:** Reasonable investigation did not produce enough evidence. Explain what was checked and qualify or omit unsupported claims.

Verification is separate from record completeness, development status, evidence provenance, and testing status.

### 8.3 Review steps

1. Check category scope and substantive MLP relevance.
2. Search existing records, aliases, versions, and same-name projects.
3. Establish project identity and actual project evidence.
4. Check sources, creator attribution, dates, downloads, and media rights.
5. Assign verification and completeness assessments separately.
6. Prepare the record using the existing schema.
7. Review the change through a pull request and run the project checks.
8. Merge and publish through the existing deployment workflow.

An issue is a proposal, not an acceptance decision. A record is not public in the catalog until it has passed review, been merged, built, and deployed.

## 9. Disclaimer and archive purpose

MLP OS Archive is an independent, non-commercial fan preservation project. Its purposes are to document MLP-related operating-system and desktop projects, preserve traceable historical information, and help users discover original creators and sources.

The archive:
- Is not affiliated with, authorized, endorsed, or sponsored by Hasbro or its subsidiaries.
- Does not guarantee that third-party projects, downloads, or links remain available or safe.
- Does not claim that every archived project has been installed or tested.
- Preserves creator attribution and applicable rights notices.

**Guiding principle:** Prefer an accurate, qualified historical record over an inflated catalog. Do not invent facts or lower evidence standards merely to increase the number of entries.
